## D. AUTHORITATIVE REPAIR-BOUNDARY EVIDENCE CHOSEN

**`git log --reverse --ancestry-path <original_commit_oid>..<current_head>`**

with `--pretty=format:%ct`, captured by the supervisor's
`_git_superseding_repair_committed_at(anchor, head)` helper.

**Why this evidence:**

- The audit explicitly preferred "an already-authoritative state
  transition" over a "weak heuristic". The supervisor's
  `git log --reverse --ancestry-path <anchor>..<head>` IS the
  authoritative way to find the FIRST commit on the PR-branch history
  that descends from the original review anchor. There is no more
  canonical answer.
- A later documentation/report-only commit does NOT shift the
  boundary: `--reverse --ancestry-path <anchor>..<head>` returns the
  EARLIEST descendant of the anchor, which is the head-changing
  repair that first made the thread stale. (Verified live: PR #7's
  superseding boundary is `b89c25f` at `2026-08-19T14:18:41Z`, not
  `70d1085` at `11:06:38Z` the next day.)
- When the anchor was rebased away (no commits between anchor and
  head), the helper returns `None` and the rule fails closed.
- When git lookup fails (timeout, non-zero exit, missing repo), the
  helper returns `None` and the rule fails closed.

## E. OPERATOR IDENTITY SOURCE + NORMALIZATION CONTRACT

### Sources (priority order, deduplicated)

1. `pr.user.login` — the PR author (REST `GET /repos/.../pulls/{n}`)
2. `viewer { login }` — the GitHub authenticated actor (one extra
   GraphQL round-trip per snapshot)
3. `REPO_OWNER` — the canonical repo owner login
4. `github-actions` / `github-actions[bot]` — automation actors
   (included because they commonly post operator explanations)

Snap payload exposes both the set (`snap["operator_logins"]`) and
the source breakdown (`snap["operator_identity_sources"]`).

### Normalization contract (`_normalize_operator_logins`)

- `None` → conservative fallback (GitHub Actions defaults)
- `list | tuple | set | frozenset` of strings → trimmed, non-empty,
  unique entries preserved
- bare `str` → conservative fallback (defends against the original
  `tuple("github-actions")` bug)
- `dict` → conservative fallback (defends against
  `tuple({"a": 1})` returning `("a",)`)
- any other truthy non-iterable (`int`, `float`, `bool`,
  custom object) → conservative fallback (defends against
  `tuple(42)` raising `TypeError`)

The same normalizer is used in both `_collect_review_findings` and
the `collect_findings` focused path — single source of truth.

## F. REPLY PAGINATION DESIGN

Per-thread pagination, separate from the outer thread-list
pagination:

1. **First page**: collected inline by the existing
   `capture_live_snapshot` GraphQL query, with the inner
   `comments.first: 25` selection extended to also include
   `pageInfo { hasNextPage endCursor }`.
2. **Subsequent pages**: walked by the supervisor's post-processing
   pass using `node(id: <thread_id>) { ... on PullRequestReviewThread
   { comments(first: 25, after: $cursor) ... } }` via the
   `_C22R1_THREAD_COMMENT_QUERY` constant.
3. **Safety cap**: `_C22R1_THREAD_COMMENT_PAGES_CAP = 12` = 300
   comments max.
4. **Fail-closed semantics**: when the cap is exhausted before
   `hasNextPage == False`, the snap records
   `review_thread_pagination_failed=True` and the thread id is
   appended to `truncated_thread_ids`. The readiness gate must
   treat incomplete pagination as a non-clean signal.
